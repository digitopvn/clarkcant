# Red-team review: Widget Library + Widget Lab plan (issue #128)

Adversarial verdict: 10 findings (2 Critical, 6 High, 2 Medium). Every finding is backed by file:line evidence from the current worktree (branch `feat-ui-add-widget-library-widget-lab-as-a-live` @ `e6894c4`).

## Finding 1: The sibling-overlay claim is unverifiable against the Settings modal it must open from
- Severity: Critical
- Location: Phase 2, "Quyết định thiết kế" (bullet on mount/sibling) and "Thực hiện" step 6; Phase 2 acceptance "Settings → Extensions mở browse mode"; plan.md constraint 2
- Flaw: The plan asserts "Mở/đóng chỉ đổi state của surface" and that a sibling surface preserves everything, but the primary entry point (Settings → Extensions → Browse) opens the library *while* `SettingsPanel`'s `Modal` is still mounted. That `Modal` installs a **document-level** `keydown` listener that closes on any Escape and traps Tab inside its own dialog node, with no `defaultPrevented` / nesting check. The plan's Phase 2 risk list mentions the Escape ordering as a risk but no phase owns `Modal.tsx` (Phase 2's file list is `Conversation.tsx`, `settings/*`, `styles.ts`, `widget-library/**`), and no test asserts Settings stays open.
- Failure scenario: User opens Settings → Extensions → Browse. (a) Pressing Escape runs Settings' listener (registered first when the panel opened) and closes Settings *and* the library; Modal's cleanup then focuses `opener.current` — the gear button — while the plan's stated contract is "focus trở về nút `Browse`" (Phase 2 Kiểm chứng), which is now unmounted. (b) Pressing Tab is intercepted by the Settings Modal's trap (it cycles focus inside `dialog.current`, which is behind the library), so the gallery is unreachable and the library's own `aria-modal="true"` dialog is announced as a second modal over an `aria-modal` one. Phase 2's unit tests are reducer-only (Node, no DOM) and Phase 6 journey 5 would pass or fail depending on listener registration order, so nothing in the matrix catches this.
- Evidence: `packages/conversation-client/src/Modal.tsx:45` (Escape closes unconditionally), `:55` (trap queries the Settings dialog), `:77` (`document.addEventListener("keydown", …)`), `:95`, `:108` (focus restored to `opener.current`), `:119-120` (`role="dialog"` + `aria-modal="true"`); `packages/conversation-client/src/Conversation.tsx:2206-2215` (SettingsPanel mounted unconditionally, `open={uiCheckOpen}`); `packages/conversation-client/src/settings/SettingsPanel.tsx:168-187` (two `useEffect` reads and no close coupling).
- Suggested fix: decide explicitly whether Settings closes when the library opens, then implement it: either unmount/close Settings before the library mounts (and define focus return to the element that opened the library *from the Settings list*, which cannot be the Settings button once it is gone), or make the library the only active dialog (Portal above the Modal, capture-phase Escape that `stopPropagation`s, and a `Modal` change so a nested surface suppresses its own Escape/Tab). Add an assertion "Settings title is still in the DOM" or "Settings is gone" — not just `data-widget-library-mode`.

## Finding 2: The plan's noun list cannot make `widgets.show` sentences command-shaped, so Phase 4's own tests and the Phase 6 parity journey are unreachable
- Severity: Critical
- Location: Phase 4, "Thực hiện" step 2 vs "Ma trận test" items 2-3 and Phase 6 journey 6
- Flaw: The plan adds `"thu vien widget"`, `"widget library"`, `"widget gallery"`, `"thu vien"` to `APP_NOUNS` and only "phrase cho `widgets.open`". `isAppCommandShaped` requires (a) a command opener derived from `PHRASES`, or (b) a control verb *plus* an `APP_NOUNS` phrase matched as consecutive whole words. `"hiện widget lịch"` and `"show the calendar widget"` contain none of the listed nouns, so they are not command-shaped at all.
- Failure scenario: `matchAppIntent("hiện widget lịch")` returns `undefined` → `resolveAppIntent` returns `{kind:"none"}` → the sentence is handed to the agent as a work request; no library opens. The issue's headline voice example ("show me the calendar widget") therefore silently does nothing, the Phase 4 tests 2-3 fail as written, and the Phase 6 parity journey fails. The plan's additional expectation — "Không có `widgetTargets` ⇒ `hiện widget lịch` vẫn trả `widgets.show` không target" — is impossible: shaping happens before target resolution, and the phrase table itself would have to carry "hien widget lịch".
- Evidence: `packages/core/src/app-intents.ts:100-122` (`APP_NOUNS`), `:208-217` (`COMMAND_OPENERS` derived from `PHRASES`), `:220-224` (`containsPhrase` requires consecutive words), `:252-270` (`isAppCommandShaped`), `:299-301` (`matchAppIntent` returns `undefined` when not shaped).
- Suggested fix: specify the shape rule for widget sentences concretely — add a noun `"widget"` (bare) so `"hiện widget <alias>"` shapes, or add `"hien widget"` / `"show widget"` / `"show the <target> widget"` to `PHRASES` so `COMMAND_OPENERS` carries them — and add the negative control (`"cho tôi xem widget biểu đồ"` ⇒ `none`) plus a positive control for each new noun to `packages/core/test/app-intents.spec.ts`, so the two directions cannot drift.

## Finding 3: `clark widget dev --builtin canvas.table@1` cannot run: the dev host renders a *package facet entry*, not a catalog renderer
- Severity: High
- Location: Phase 5, "Thực hiện" steps 2-3 and "Kiểm chứng" (the manual `--builtin` command)
- Flaw: `startDevHost` resolves the package at `root`, reads `pkg.facets[0]`, throws when there is none, and serves the frame as `/${facet.entryPath}` with fixture files read from the package directory. Built-in catalog widgets have no package, no facet and no entry path — their renderers are React components inside `packages/conversation-client/src/renderers.tsx`. The plan's Phase 5 file ownership includes `dev-host.ts` and `cli.ts` but no step constructs a synthetic facet/entry or a bundle of the production renderer for the iframe; the test matrix only compares reducer state, never that a built-in renders.
- Failure scenario: Running the plan's own verification command (`node packages/widget-cli/src/cli.ts dev --builtin canvas.table@1 --fixture empty`) either throws "no widget facet is declared in …" or starts a host whose frame loads nothing, so the promised convergence ("author thấy cùng bộ fixture như trong Lab") is not delivered while both listed test suites stay green.
- Evidence: `packages/widget-cli/src/dev-host.ts:166-171` (`readPackage(root)` + `facets[0]` throw), `:266-274` (`entryUrl: /${facet.entryPath}`, `fixtures` from the package), `:280-300` (package files resolved and containment-checked) ; `packages/widget-cli/src/dev-shell.ts:256-275` (sandbox/frame shell) ; `packages/conversation-client/src/renderers.tsx:935-952` (renderers are client React components).
- Suggested fix: Either narrow Phase 5 to sharing only the *preview vocabulary* and explicitly state that `--builtin` renders a declarative/text fallback (not the production renderer), or specify the entry mechanism (a generated synthetic facet + a prebuilt renderer bundle served inside the dev host's root containment check) and add a dev-host test that fetches the page and asserts the widget actually drew.

## Finding 4: Previews bypass the production dataset resolution path, and the gallery/media E2E is satisfied by the failure state
- Severity: High
- Location: Phase 2, "Thực hiện" step 2 (`WidgetPreview`), Phase 1 fixture contract; Phase 6 journey 3
- Flaw: In production the renderer's dataset is resolved from `instance.props.datasetRef` through the host's dataset map before it is adapted to `RendererDataset` (rows/freshness/updatedAt only). The plan's `WidgetPreview` instead hands the renderer a fixture-local `dataset` (with `datasetId`/`columns`) while `props.datasetRef` from the fixture resolves to nothing — the plan's own Phase 1 risk bullet admits this and proposes inline data as the mitigation. It also never passes `imageUrl`, the resolver that picture widgets require.
- Failure scenario: `canvas.gallery@1` / `canvas.image@1` previews render `Unavailable` ("Chưa tải được hình ảnh…") because `imageUrl` is undefined — a stated failure, not a live preview — yet the E2E assertion passes because `data-widget-role="media"` sits on the outer `Frame` that also wraps the unavailable text. Any widget whose rendering depends on host-resolved refs is therefore "verified" while showing its error state, and the library never proves the resolution contract it claims to exercise.
- Evidence: `packages/conversation-client/src/Conversation.tsx:1610-1612` (`const datasetRef = instance.props.datasetRef; … datasets[datasetRef]`), `packages/conversation-client/src/renderers.tsx:33-45` (`RendererDataset`), `:106` (role on `Frame`), `:711-716` (`LocalImage` → `Unavailable`), `:793-795` (`Gallery` → `Unavailable` when no url); `packs/data-canvas/src/index.ts:36` (`required: ["datasetRef"]`) ; plan Phase 2 step 2 (preview passes props/dataset/state only).
- Suggested fix: Have `WidgetPreview` pass `imageUrl` (a fixture-scoped resolver over local fixture refs) and a dataset map keyed by the fixture's own `datasetRef`, so the preview exercises the same "ref → resolved rows" hop production does; assert per-entry container attributes (`data-widget-preview="<definitionId>"` plus absence of `data-widget-unavailable`) instead of a shared `data-widget-role`.

## Finding 5: `catalogCoverage()` measures a family vocabulary that intersects neither existing required list, so the "release gate" cannot gate
- Severity: High
- Location: Phase 1, "Ma trận test" item 4 (`coverage.spec.ts`) and item 1 (registry family vs `FAMILY_BY_DEFINITION`); Phase 5 "Thực hiện" step 6 (family strip filter)
- Flaw: The plan derives families from `FAMILY_BY_DEFINITION` (trend/tables/media/cta/metrics/filter/layout/calendar) and asserts coverage against that same map, which makes the registry test self-referential and vacuous. Two other taxonomies already exist and are the ones the repo documents: `REQUIRED_CATALOG_FAMILIES` (18 documented families: charts, map, notes-editor, diagram, …) and `COMPOSITION_FAMILIES` (trend/media/cta/filter/metrics/calendar). No phase imports either or states which list `catalogCoverage()` reports against, and the only consumer of `familiesWithoutFixtures` today is a test with an invented list.
- Failure scenario: The gate reports "missing" for the catalog's own vocabulary and green for the documented families, or vice versa; adding `"canvas.note@1": "note"` (Phase 1 step 1) introduces a 15th family name that exists in neither required list, so its "implemented" verdict is meaningless. Phase 5's `Installed`/`Local` "families" are provenance values, not families, so the family strip mixes two orthogonal axes and the filter cannot be validated by the plan's own test 3 ("filter family `media` chỉ còn entry media").
- Evidence: `packs/data-canvas/src/index.ts:397-412` (`FAMILY_BY_DEFINITION`), `packages/widget-host/src/index.ts:248-262` (`REQUIRED_CATALOG_FAMILIES`), `:230-236` (`COMPOSITION_FAMILIES`), `:74` (`familiesWithoutFixtures`), `packages/widget-host/test/seams.spec.ts:485` (only caller, invented list), `docs/widgets-and-extensions.md:95-160` (§4 / §4.1 the required list is derived from).
- Suggested fix: Name the single required-family source (import `REQUIRED_CATALOG_FAMILIES` and map catalog families onto it, or state that coverage is scoped to shipped families only), make the miss explicit in the report (12 of 18 documented families have no definition), and keep provenance (`source`) out of the family axis.

## Finding 6: Installed/local provenance has no browser-visible data source, so Phase 5's acceptance is unreachable while its unit test stays green
- Severity: High
- Location: Phase 5, "Quyết định thiết kế" (Provenance) and "Thực hiện" steps 1 and 6; plan.md acceptance "provenance installed/local"
- Flaw: `client.packages()` returns `InstalledPackageView[]`, a *package*-level record (packageId/version/digest/codeGeneration/activatedAt/source/lane). It carries no facet or widget-definition list, and no other client-readable route exposes one. `mergeInstalledEntries(builtin, installed)` therefore has no way to know which catalog entries an installed package provides; it can only fabricate entries or mark every one `metadataIncomplete`.
- Failure scenario: The library shows zero installed/local entries and no version/digest/lane labels, while `packages/widget-catalog/test/provenance.spec.ts` passes because it feeds a hand-written installed list with definition ids. The plan's Phase 6 E2E journeys (1-6) cover only built-ins, so the acceptance criterion "installed/local provenance" is declared done on phantom evidence.
- Evidence: `packages/conversation-client/src/api.ts:352-361` (`InstalledPackageView`), `:1085` (`packages()`), `packages/core/src/installed-packages.ts:44-99` (the mapped return shape, no definitions), `apps/runtime/src/gateway.ts:1442-1451` (`GET /packages` returns exactly that), `apps/runtime/src/node-tools.ts:972` (facets exist only on the agent-facing node-tools path).
- Suggested fix: Add the missing read (e.g. installed facets/definitions on the packages route or a new one) to Phase 5's ownership and steps, plus one browser E2E that installs/activates a fixture package and asserts an "Installed package" card with version/digest/lane; otherwise cut installed/local from the phase and say so in the plan.

## Finding 7: `client.packages()` async race is unhandled — no cancellation, no error state, no cancellation test
- Severity: High
- Location: Phase 5, "Rủi ro và rollback" (async note) and "Thực hiện" step 6
- Flaw: The plan acknowledges the async failure only as a risk sentence. It specifies neither a `cancelled` guard/cleanup (the pattern the same codebase already uses for both Settings reads and the existing installed-packages section) nor the error state the risk text promises ("installed là phần bổ sung có trạng thái lỗi riêng"), nor any test. Phase 5's test 4 is fixture-driven, so no test executes the async path.
- Failure scenario: On a slow or unreachable node, the packages response lands after the surface closed (state written for a surface the user already dismissed) or after the user narrowed the family filter to `Local`, silently repopulating it; a rejected call either leaves the built-in gallery blocked behind an error or is swallowed with no message, which is the "empty screen and unreachable node look identical" failure the repo explicitly designs against.
- Evidence: `packages/conversation-client/src/settings/SettingsPanel.tsx:126-146` and `:150-166` (established `cancelled` + separate error state pattern), `packages/conversation-client/src/settings/ExtensionsSettings.tsx:127-148` (existing `packages()` read with `cancelled` guard and its own failure copy), plan Phase 5 "Rủi ro" (single bullet, no design or test).
- Suggested fix: Specify the async contract: an abort/`cancelled` guard, a distinct "installed list unavailable" state next to the built-in grid, a retry affordance or an explicit no-retry decision, and a unit test that drives a rejecting and a late-resolving `packages()` through the client-side merge path.

## Finding 8: Container `canvas.overview@1` makes the fixture rule and the "browse shows only renderable" rule contradict each other
- Severity: High
- Location: Phase 1 test item 2 ("mọi entry có ≥1 fixture"); Phase 2 "Quyết định thiết kế" (missing-renderer error block); Phase 5 "Quyết định thiết kế" (browse shows only renderable)
- Flaw: `OVERVIEW` is a member of `WIDGETS` and has no entry in the client renderer map — the catalog coverage test special-cases it for exactly that reason. Phase 1 requires a fixture for *every* entry, Phase 2 mandates a visible error block when `resolveRenderer` returns nothing, and Phase 5 says browse mode shows only renderable entries. The plan never defines the renderable predicate or where it lives, even though Phase 1 forbids `packages/widget-catalog` from knowing about renderers.
- Failure scenario: Either the container card appears in normal user browse mode as a permanent "missing renderer" block — violating constraint 8 ("không hiển thị widget chưa implement như thể chạy được") — or it is filtered out and its mandatory fixtures are dead data that a test can never render, which turns the fixture gate into a count with no meaning. The E2E assertion "không có `data-widget-preview-missing`" cannot decide between the two, because filtered-out entries produce no attribute at all.
- Evidence: `packs/data-canvas/src/index.ts:99` (`OVERVIEW`), `:373-388` (`OVERVIEW` inside `WIDGETS`), `packages/conversation-client/test/catalog-coverage.spec.ts:36-42` (container special-cased as having no renderer), `packages/conversation-client/src/renderers.tsx:935-951` (no `canvas.overview@1` key), `packages/conversation-client/src/Conversation.tsx:1512-1520` (the composition path checks the container before the leaf lookup).
- Suggested fix: State the rule in the data contract (`WidgetCatalogEntry` needs an explicit renderability marker or the gallery must take a `renderable(id) => boolean` predicate supplied by the client), exclude the container from the fixture requirement, and add a test that asserts the container is absent from browse mode and present (labelled honestly) in developer mode.

## Finding 9: The Phase 3 test matrix cannot execute in this repo — no DOM environment, no React test renderer
- Severity: Medium
- Location: Phase 3, "Ma trận test" items 2-5, 7, 9; Phase 5 test item 4
- Flaw: The listed assertions ("props của preview đổi theo fixture mới", "bề rộng khung preview đổi đúng theo `PREVIEW_WIDTHS`", "thuộc tính theme của surface đổi", "surface đặt cờ reduced-motion", "assert control vắng mặt") are component/DOM assertions placed in `packages/conversation-client/test/widget-lab.spec.ts`. Vitest runs with `environment: "node"` and the repo has no jsdom/happy-dom/@testing-library dependency; the only DOM tool is Playwright.
- Failure scenario: Implementers must either delete these cases to make the phase's verification command pass (leaving "mọi control đều thật" verified only by the Phase 6 Playwright journey, which covers only `canvas.table@1` and `canvas.line@1`), or add a DOM test stack mid-implementation — a dependency and config change no phase budgets or reviews. Same problem for Phase 5's "browse chỉ hiện entry renderable; developer hiện entry isolated với nhãn trung thực".
- Evidence: `vitest.config.ts:59` (`environment: "node"`), `vitest.config.ts:44-56` (include globs for Node specs), `package.json:37-46` (devDependencies: playwright/eslint/tsx/typescript/vitest only), Phase 3 "Kiểm chứng" (`vitest run packages/conversation-client/test`).
- Suggested fix: Either restate these as pure selector/reducer assertions (export `visibleEntries`, `previewWidthFor`, `themeAttributeFor`, `isControlAvailable` and test them in Node), or budget an explicit DOM-test dependency for the phase and name it in the phase's file/step list.

## Finding 10: Phase 4's executor expectation ("host thiếu method ⇒ không ném") contradicts how `runAppIntent` is built
- Severity: Medium
- Location: Phase 4, "Ma trận test" item 3
- Flaw: `runAppIntent` calls host methods directly in its switch and has a `never`-guarded `default` that *throws*; optionality exists only for the window kinds, and `hostHasCapability` returns `true` by default for every other kind. Adding `widgets.open`/`widgets.show` cases that call `host.openWidgetLibrary(...)` therefore throws a `TypeError` for any host that does not implement the new method, rather than returning `{ran:false, say:…}` as the plan's test requires.
- Failure scenario: Any embedding that constructs an `AppIntentHost` without the new method (desktop shell embedding an older client bundle, or any host built before this change) receives `widgets.open` and throws inside the shared executor instead of answering with a sentence — a regression on a documented property of the executor ("a host simply omits the methods it cannot provide") in exactly the version-skew case the registry exists to keep honest.
- Evidence: `packages/conversation-client/src/app-intents.ts:84-104` (direct `host.openSettings()` calls), `:126-131` (`default` throws via the `never` guard), `:134-152` (`hostHasCapability` returns `true` by default; only `window.*`/`app.quit` are optional), `packages/conversation-client/src/Conversation.tsx:968-1010` (the host object literal).
- Suggested fix: Make `openWidgetLibrary?` optional on `AppIntentHost`, add it to `hostHasCapability` with a named sentence (a "this build cannot open the library" message analogous to `NOT_DESKTOP_SAY`), and keep the `never` guard honest by adding the two cases to both switches in the same change.
