## Finding 1: the matcher's shape test makes the plan's own `widgets.show` examples unreachable
- Severity: Critical
- Location: Phase 4, "Ma trận test" bullets 2/3/4 and "Thực hiện" item 2
- Flaw: Phase 4 adds `"thu vien widget"`, `"widget library"`, `"widget gallery"`, `"thu vien"` to `APP_NOUNS` (phase-04:41) and states the plan adds a *phrase* entry only for `widgets.open` ("thêm phrase cho `widgets.open`"), while instructing "giữ nguyên luật `isAppCommandShaped`". `isAppCommandShaped` demands either an opener derived from the phrase table's first two words, or a control verb **plus** an `APP_NOUNS` whole-word hit. `"hiện widget lịch"` and `"show the calendar widget"` satisfy neither: bare form `hien widget lich` contains none of `thu vien widget` / `widget library` / `widget gallery` / `thu vien`, and the bare word `widget` is not in `APP_NOUNS`.
- Failure scenario: `matchAppIntent("hiện widget lịch")` returns `undefined`, the sentence is handed to the agent as a work request, and both the phase-4 unit test (`"hiện widget lịch"` ⇒ `widgets.show` with `canvas.calendar@1`) and phase-6 E2E journey 6 (`"hiện widget lịch"` opens the calendar) fail. The implementer either ships a red gate or silently widens `APP_NOUNS`/`CONTROL_VERBS` — the same rule the plan says it is protecting ("Giữ nguyên luật cũ thay vì nới nó").
- Evidence: `packages/core/src/app-intents.ts:100-112` (`APP_NOUNS`), `:114` (`APP_COMMAND_MAX_WORDS`), `:209` (`COMMAND_OPENERS` derived from `PHRASES`), `:252-268` (`isAppCommandShaped`), `:300` (`matchAppIntent` returns `undefined`); plan claims at `phase-04-app-intents.md:17,24,28,41`.
- Suggested fix: state the noun/opener change that makes both examples reachable (`"widget"` in `APP_NOUNS`, plus `"hien widget"`/`"show me the"` openers) and test it explicitly, or replace the two test examples with sentences the current rule can actually pass.

## Finding 2: provenance is modelled on fields that do not exist, and installed entries cannot be built from `client.packages()`
- Severity: Critical
- Location: Phase 5, "Ma trận test" item 3, "Thực hiện" items 1-2; Phase 1 "Hợp đồng dữ liệu"
- Flaw: Phase 5 requires merged installed entries to carry `packageVersion` / `sourceRef` / `digest` / `trustLane`. None of `packageVersion`, `sourceRef` or `trustLane` exists anywhere in the repo; the real object is `InstalledPackageView { packageId, version, digest, codeGeneration, activatedAt, source: { sourceTier, rationale, artifactUrl }, lane, consentedDigest }`. Worse, `WidgetCatalogEntry.definition: WidgetDefinition` and `family: string` are required in the phase-1 contract, but the installed-package view carries no definition, family or renderer, and no route exposes per-package widget definitions.
- Failure scenario: a `ProvenanceInfo`/structural copy typed with `trustLane` is always `undefined` (or fails to typecheck against the real object), the provenance test passes only against invented fixtures, and browse mode cannot construct a `WidgetCatalogEntry` for an installed package at all — so phase 5's "installed merge" either fabricates a definition or never renders. That is precisely the "inventing another trust model" the issue forbids.
- Evidence: `packages/conversation-client/src/api.ts:352-363`; `grep -rn "trustLane" --include=*.ts` → 0 hits; `packages/core/src/installed-packages.ts:32-37` (lane, consentedDigest, no definitions); `packages/contracts/src/install.ts:32` (`isolationClassSchema` is the isolation vocabulary that does exist); `plan/phase-05-devhost-and-provenance.md:22`.
- Suggested fix: bind provenance to the real `InstalledPackageView` (`version`, `source.sourceTier`, `digest`, `lane`), and either make installed entries a discriminated union without a `WidgetDefinition`, or state the node route that would supply installed definitions (today: none).

## Finding 4: the Lab's theme and reduced-motion controls have no mechanism to be "real"
- Severity: High
- Location: Phase 3, "Quyết định thiết kế" (last bullet: "theme đổi class theme thật, reduced-motion bật chế độ thật")
- Flaw: The token sheet applies themes as `:root[data-cc-theme="light"]` (root-scoped only) and reduced motion only inside `@media (prefers-reduced-motion: reduce) { :root { --cc-motion-*: … } }`. A Lab control that sets an attribute on a preview subtree therefore changes nothing for that preview. Neither phase 2 nor phase 3 owns a `@clarkcant/design-tokens` change, and the plan's own tests only assert the attribute ("surface đặt cờ reduced-motion") — a label-only control, which the issue's non-goals and the plan's constraint #8 forbid.
- Failure scenario: a developer switches the preview to light or reduced motion; the card keeps the page theme and keeps animating; the assertion passes because it only checks `data-*`. The delivered "viewport/theme/reduced-motion can be previewed" acceptance criterion is false while every gate is green.
- Evidence: `packages/design-tokens/src/css.ts:85` (`:root[data-cc-theme="${theme}"]`), `:95-101` (reduced set only inside the media query); `packages/conversation-client/src/theme.ts:114` (attribute set on `documentElement`); `packages/conversation-client/src/styles.ts:1487` (media query only); `plan/phase-03-widget-lab.md:16` vs `:37-40`.
- Suggested fix: state where the scoped override lives (e.g. new subtree selectors `[data-cc-theme]`/`[data-cc-reduced-motion]` in `design-tokens`, or render the preview in a frame) and assert the computed value/behaviour, not the attribute.

## Finding 5: mounting the library beside an open Settings modal creates two competing dialogs
- Severity: High
- Location: Phase 2, "Thực hiện" item 6 and "Rủi ro" (Escape bullet)
- Flaw: `SettingsPanel` renders its content inside `Modal` and the plan keeps Settings open while adding `<WidgetLibrarySurface>` as a sibling. `Modal` adds a document-level `keydown` handler that closes on Escape and cycles Tab **inside the settings dialog node**, moves focus into that dialog on open, renders its own scrim, and sets `body.overflow`. With Settings still open, both surfaces claim `role="dialog" aria-modal="true"`, the scrim still covers the page, and Tab cannot reach the library's own trap semantics correctly. The plan's mitigation is literally "kiểm tra thứ tự listener" — a manual check, not a mechanism.
- Failure scenario: Settings → Extensions → `Browse` shows the library but keyboard focus/Tab remain bound to the settings dialog behind it; one Escape is consumed by both handlers (settings may close under the library, or neither); phase-6 E2E journey 5 (keyboard-only open/navigate/close) and journey 6 (click parity) fail or flake.
- Evidence: `packages/conversation-client/src/settings/SettingsPanel.tsx:189,198`; `packages/conversation-client/src/Modal.tsx:43-77` (Escape + Tab cycling), `:95-104` (focus into dialog, scroll lock), `:112-120` (scrim, `aria-modal`); `plan/phase-02-browse-surface.md:38,53`.
- Suggested fix: declare the transition (closing Settings when the library opens, or rendering the library *inside* the settings dialog region and suspending the underlying trap), and cover it with a keyboard assertion.

## Finding 8: copying `SAMPLE_DATASET` creates a second dataset source; the non-duplicating import trips an invariant
- Severity: Medium
- Location: Phase 1, "Thực hiện" item 5 ("dùng `SAMPLE_DATASET` dạng bản sao thuần")
- Flaw: `SAMPLE_DATASET` is one object consumed by the runtime that registers the sample dataset for the whole node; "a pure copy" in `widget-catalog` means the Lab's preview rows can silently diverge from what the conversation actually renders. The clean alternative — importing `@clarkcant/data-canvas/sample` — is blocked by the repo's browser-entry invariant, which walks imports textually (including `import type`) from `apps/web/src` through `exports` maps; `sample.ts` has `import type { SampleRecipe } from "@clarkcant/core"`, and `core`'s barrel re-exports modules that read `node:fs`/`node:crypto`. The plan lists `pnpm run invariants` as a phase-1 check but never mentions this coupling.
- Failure scenario: fixtures render rows the product never shows (drift nobody tests), or an implementer "fixes" it by importing `sample.ts` and `pnpm run invariants` fails with "imports node:fs — reached from apps/web/src/main.tsx".
- Evidence: `packs/data-canvas/src/sample.ts:21-33` (`SAMPLE_DATASET`), `:4` (type-only core import); `apps/runtime/src/services.ts:322-327` (the same object registered as the node's sample dataset); `tools/check-invariants.mjs:353-361` (entry walk + the `from "…"` regex + offender reporting); `packages/core/src/index.ts:11-16` (barrel), `packages/core/src/directory-index.ts:1` (`node:fs`).
- Suggested fix: re-export the one dataset from `@clarkcant/data-canvas/sample` behind a browser-safe subpath (the way `@clarkcant/widget-host/session` is split for exactly this reason), and make it a phase-1 check to run `pnpm run invariants` after the new dependency edge lands.
