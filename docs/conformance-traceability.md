# Conformance traceability

Evidence table for the scope items and acceptance tests in
[implementation-plan.md](implementation-plan.md). Each status must be read together with its
test and limits; having a test does not prove the current run passed.

**Status vocabulary**

- **PASS** — exercised by a test that runs in this repository. The test name is given.
- **BLOCKED** — cannot be exercised without external infrastructure, credentials or hardware. The condition is named.
- **NOT-IMPLEMENTED** — belongs to a phase that this bootstrap did not build.
- **PARTIAL** (scope items only) — some layers are real and tested while others are absent; the split is stated.

This table is checked by `pnpm invariants`, which fails if any identifier is missing.
A status here is never upgraded without the corresponding test appearing alongside it.

**Status now has a machine-readable source.** The status of each scope item (`V01`–`V18`) and of each
capability claim in source code lives in
[`packages/contracts/src/implementation-status.ts`](../packages/contracts/src/implementation-status.ts);
the `V` rows of this table are the readable copy of the same data. `pnpm invariants` fails when the two
disagree, when an `implemented` entry does not name a real test — and the test name must be in the very file
named, so “the schema exists” does not get through — or when a
`partial`/`blocked`/`not-implemented` entry does not name what is missing. Rows `T01`–`T75` have **no**
corresponding registry entry: they are still checked only by the presence of a `| Tnn |` row in the
table — not by an id string appearing somewhere in the document — and by the test
titles quoted in the table, so a quoted title must exist in the repo — while a row that only names a
spec path is not yet matched against any specific test case. Comments in source only point at the
registry with `@status-ref <capabilityId>`, and do not assert a status themselves.

**External gates remain open.** #2 (a real Google Calendar account), #3 (Computer Use signing), #4 (a real voice
provider) and #5 (NodeLink across two real hosts) remain open and remain linked; no row here is upgraded
because a fixture ran green. The registry carries the issue number and the reason for what is missing for each gate.

The unproven part of widgets is named right at the gap: `interaction.detach` is now genuinely closed —
the dev host has its own detached host window (`clark widget dev`'s `/detached` route) and a lease
read/written through the same `claimLiveOwner`/`releaseLiveOwner` of `@clarkcant/core` that `apps/desktop/src/main.mjs`
also calls ([dev-lease.ts](../packages/widget-cli/src/dev-lease.ts)), proven with real Chromium
([detach-real-browser.e2e.spec.ts](../packages/widget-cli/test/detach-real-browser.e2e.spec.ts)). Exactly
one gap remains: `voiceClickParity` needs a voice session, whose prerequisite is a provider account
(#4) — so `V12` remains `PARTIAL`, with that gap alone.

## Summary

### Known gap: widget performance (Phase 14)

The three Phase 14 performance items live here rather than in the table, because they have **nothing to attach to yet**:

- **pointer Orb loop outside React state** — in place and tested (`apps/web/e2e/orb.spec.ts`, the canvas is not rebuilt
  when the pointer sweeps across it 20 times).
- **no duplicate live subscription after detach** — in place and tested for some time
  (`core.spec.ts`: "holds the one-owner rule across a detached surface too (V20)"). Detach presents the same
  instance somewhere else, does not create a second instance, and the lease refuses a second owner, naming the surface that holds it.
- **heavy widget lazy mount** and **offscreen suspend** — **in place**: a live surface mounts only when it enters the viewport and
  suspends when it leaves (`apps/web/e2e/mini-app.spec.ts`: "a pinned surface mounts near the viewport and suspends when
  it leaves"), and the isolated frame mounts inside that same surface. The two conditions that used to be missing are now in place: the node serves
  the entry of an installed package (`GET /packages/:id/:version/files/*`, with a nonce-based CSP on each response), and
  a real widget's frame runs from the conversation (`apps/web/e2e/widget-frame.spec.ts`: "a widget package runs in a
  sandboxed frame, and its code is the package's").

The tables above are where each requirement's status is looked up; no scope item is declared
complete. Fixtures prove the application's wiring; they do not replace verification against
the real provider. The UX direction in [DESIGN.md](../DESIGN.md) does not upgrade conformance status
on its own without implementation evidence.
